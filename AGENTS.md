# AGENTS.md

## Scope

This repository contains one minimal Home Assistant custom integration and its bundled Lovelace card. Keep all work inside this repository. Never modify or reuse files from the sibling `casa-voz-card.js` project.

Supported product areas are limited to Jellyfin recent/playing, Radarr/Sonarr upcoming, the carousel mode, image delivery, and card presentation. Do not add qBittorrent, Bazarr, TMDB, infrastructure monitoring, entities, automations, notifications, or playback controls without an explicit scope decision.

## Architecture

- Backend runtime lives in `custom_components/octopus_media/`.
- Frontend source lives in `frontend/src/`.
- Backend/frontend contracts are defined in `models.py` and `frontend/src/models.ts` and documented in `docs/architecture.md`.
- Polling is shared per ConfigEntry and separated by category.
- Credentials and external URLs never cross into the card.
- Image endpoints accept only registered opaque references and closed variants.
- `mode` selects data; `layout` selects presentation.
- Layouts consume shared view models and must not make WebSocket calls.

## Development environment

Home Assistant 2026.7.x requires Python 3.14.2 or newer. Do not run HA tests under an older Python and report them as valid.

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest
ruff check .
ruff format --check .
mypy custom_components tests

pnpm --dir frontend install
pnpm --dir frontend lint
pnpm --dir frontend test
pnpm --dir frontend build
pnpm --dir frontend verify:bundle
```

Native Windows pytest collection requires `tests/windows_compat` on `PYTHONPATH`
because Home Assistant imports POSIX-only modules. The shims are collection-only,
must never be used to run Home Assistant, and must not be enabled in Linux CI.

## Style

- Python: typed async code, Ruff formatting, no synchronous HTTP clients.
- TypeScript: strict mode, Lit, immutable config copies, no private Home Assistant frontend APIs.
- Keep localized strings in the localization modules or integration translation JSON files.
- Keep fixtures fictional and deterministic.
- Prefer small modules and pure normalization/layout functions.

## Security

- Never log API keys, passwords, cookies, signed URLs, ref secrets, or raw diagnostic payloads.
- Never accept arbitrary external URLs in image or WebSocket requests.
- All WebSocket commands and HTTP views require Home Assistant authentication.
- Never place credentials in card YAML, frontend source, fixtures, screenshots, or examples.
- Do not access a real media server from tests.

## Generated files

`dist/octopus-media-card.js` and `custom_components/octopus_media/frontend/octopus-media-card.js` are generated by one frontend build. Both files must be byte-identical. Do not hand-edit either file.

## Visual snapshots

Update screenshots only after reviewing the diff at every target size. Record intentional changes in the changelog. Never update snapshots merely to silence a failure.

## Never commit

- `.env*` except `.env.example`;
- tokens, diagnostics, private fixtures, real service URLs or IDs;
- `.venv`, `.python`, `.tools`, `node_modules`, coverage, Playwright reports;
- changes from the sibling project;
- bundles that do not match byte for byte.

## Definition of done

- relevant lint, types, tests, build, and bundle verification pass;
- no secrets or real environment data are present;
- partial failures and stale data are represented explicitly;
- long titles remain available and accessible;
- teardown cancels subscriptions, observers, timers, and requests;
- documentation and fixtures match the versioned contract.

## Home Assistant environments

HA-LAB
- MCP = `ha_lab_mcp`
- ambiente padrão para desenvolvimento, testes e validação.

HA-PROD
- MCP = `ha_mcp`
- ambiente real da casa.

Regras obrigatórias:

- desenvolvimento -> HA-LAB
- testes -> HA-LAB
- deploy experimental -> HA-LAB
- HACS experimental -> HA-LAB
- Lovelace/Resources experimentais -> HA-LAB
- ConfigEntry experimental -> HA-LAB
- reprodução de bugs -> HA-LAB
- correções -> HA-LAB
- restart decorrente de desenvolvimento -> HA-LAB

HA-PROD pode ser usado para observar estados reais, diagnóstico, leitura de
configuração e operação doméstica explicitamente solicitada pelo usuário.

Para problemas encontrados em produção:

OBSERVAR PROD
→ REPRODUZIR LAB
→ CORRIGIR LAB
→ VALIDAR LAB
→ REPORTAR

Nunca promover LAB → PROD automaticamente.

A existência de ferramentas mutáveis no MCP de produção não constitui
autorização para usar produção como ambiente de desenvolvimento.

Antes de qualquer operação mutável de engenharia, definir `TARGET = HA-LAB`
ou `TARGET = HA-PROD`. Se `TARGET = HA-PROD`, parar e pedir autorização
específica.

## Shared HA-LAB environment

HA-LAB is shared by multiple development projects.

The Octopus project owns only its own integration, frontend bundle,
configuration entries, test helpers, and OCTOPUS LAB dashboards/views.

Another frontend project — the kitchen dashboard — is developed in the
same HA-LAB and must not be modified, removed, reset, migrated, cleaned,
or used as an Octopus test target.

Before changing any global Home Assistant frontend resource, Lovelace
resource, theme, HACS component, /config/www asset, or shared dashboard
configuration, determine whether it belongs to or is used by another
project.

Do not perform broad cleanup or reset operations in HA-LAB.

When ownership is unclear, preserve the existing resource and use an
Octopus-specific resource/name/path instead.
